# Dantagger: game plan

Status: the plan of 2026-10-21. The user answered §9 the same day and the
library was then built. **The current state, decisions, blockers and the
conventions found against Swabian are in `AGENTS.md`; usage is in
`README.md`.** Where the answers changed the plan, they win:

- Q1: negative channel → positive channel, with a banner.
- Q2: up to 10 M/s on USB 3; unmissable overflow banners.
- Q3/Q7: `setHysteresis(channel, ohms)`, clamped; defaults 0.01 V and
  1000 Ω on every open.
- Q4/Q5: out-of-range triggers and setting changes during a run raise
  errors.
- Q6: stream only while measuring.
- Q8: Swabian stays the default; the hook exists but is not installed.
- Q9: parity was checked against the Swabian library as an oracle.
- Q10: `drivers/amcc` is out of scope; `setHighResolution(1|2|4)`; host code
  copied into `third_party/`.

Companion file: `SWABIAN_API_USAGE.md` (the exact Swabian API used by each
script, generated by `tools/scan_swabian_usage.py`).

Dantagger is a drop-in replacement for the parts of the Swabian `TimeTagger`
Python library that the SDE measurement scripts use. It runs on the TDC board
in `../../FPGA/TDC_Firmware` (Alchitry Au V2 + Ft+ FT601 + comparator board +
TDC-GPX2 daughterboard, firmware design `0x54440001`).

## 1. The user's instructions (2026-10-21), kept as a checklist

1. Go through every script here that uses the Swabian library and document
   exactly which functions it uses. → `SWABIAN_API_USAGE.md`.
2. Study `FPGA/TDC_Firmware`: the firmware, the host app
   (`build/host/app`) and the libraries around it.
3. Write a new time-tagger library, **Dantagger**, in `./Dantagger`. It
   implements the Swabian measurement classes so that it can be dropped in
   for the Swabian library and the existing scripts run on the new board.
4. Recreate **only** the functions the measurements use, plus the
   infrastructure they need.
5. **Do not look at the Swabian library's source code.** (The manual
   `Swabian_TimeTagger_User_Manual.pdf` is the specification.)
6. Same overall design as Swabian: a **very fast, efficient C++ library**
   behind a user-friendly Python library. Speed and efficiency come first.
7. Tags come off the device and go through C++ measurement classes
   (Correlation, Histogram, Countrate, …). **Test and benchmark them with
   simulated data, and use the benchmarks to make them faster.**
8. **Do not save time tags anywhere.** Tags are processed by the
   measurements and the results go to the user through Python (the scripts
   save the results themselves).
9. The Python library **applies default settings and calibrates the board
   the first time it is opened after it is plugged in** (the current
   gateware needs this). If one script opens the board and runs to
   completion and then another script runs without the board being
   unplugged, Dantagger must **recognise that the board is already
   configured and calibrated and skip both steps**.
10. This step: write this plan, list the features sorted by how
    straightforward they are, list the ambiguities, and **wait for the
    user's answers before implementing anything**.

- Negative channels (falling edge): `ch_stop2 = -1` in the 2-D tomography
  scripts, `ch_stop = -1` in `1dtomography_measure_hist.py`; `-2`, `-4` in amcc.
- Software delays of ±31.55 µs (`tOffset1/2` in `tomography_measure_hist.py`).
- Auto-correlation on one channel (`ttHist(channel1=c, channel2=c)`).
- `getData()` read while a measurement is still running
  (`pulsePicker_streamCountrate.py`).
- Trigger levels from −0.15 V to +0.8 V, many at 9–23 mV (SNSPD pulses);
  `ttHist(invertedTrigger=True)` sets −0.5 V.
- Dead times of 0–30 ns through `setInput(v, t)`.
- Bin widths 3 ps … 600 ps, up to 3000 bins (1-D) and 500 × 500 (2-D).
- The start channel is the laser after the pulse picker: `REPRATE_HZ =
  2733334` (2.73 MHz).

## 3. What the board gives us, and where it differs from a Swabian

From `PROTOCOL.md`, `AGENTS.md`, `host/README.md` and the 2026-10-20 hardware
notes in `TDC_Firmware`.

| Topic | TDC board (release 1) | Consequence for Dantagger |
|---|---|---|
| Inputs | 4 channels, STOP1–STOP4. The GPX2 timestamps one edge only. **STOP3 is inverted at the comparator**, so it timestamps the opposite edge | No per-channel edge choice. Swabian `-n` (falling edge) exists only as STOP3. See Q1 |
| Trigger | Comparator DAC, safety window **−0.100 … +1.500 V**, ~38 µV steps; there is no override | −0.15 V and −0.5 V requests are out of range. See Q2 |
| Hysteresis | Settable per channel (TLV3901 HYS resistor). 75 Ω ≈ 45 mV hysteresis: a 10 mV trigger then **never re-arms**. ≥ 4 kΩ ≈ 1 mV: chatters on noise | Swabian has no such knob, but scripts at 10 mV need a working default. See Q3 |
| Time base | GPX2 against an 8 MHz REFCLK, 1 ps LSB, 24-bit reference index (wraps every 2.1 s), unwrapped with the FPGA's 100 MHz coarse clock | int64 ps timestamps, as Swabian |
| Resolution | Internal step ≈ 44 ps with HIGH_RESOLUTION off (measured). The datasheet gives ~20 ps rms off and ~9 ps rms at 4× | Natural mapping to `Resolution`. See Q5 |
| Rate per channel | 100 MHz SDR LVDS: one frame per event; 44-bit frames → **2.27 M events/s per channel** | **The 2.73 MHz laser start is above this.** Shorter frames are a configuration change. See Q4 |
| Total rate | FT601 at USB 2 (enumerated at 480 Mb/s): ~45 MB/s ≈ 5.6 M records/s. FPGA FIFO 8193 records; drops are reported in-band (OVERFLOW markers) but **not per channel** | Overflow handling as in Swabian; rates are lower bounds while dropping. See Q8 |
| Ordering | Records are almost time-ordered (≤ 8 coarse cycles out); events trail their stop edge by the GPX2 latency (< 1 µs unless its FIFO backs up) | A host-side merge stage with a watermark is required anyway; software delays use the same stage |
| Control while streaming | The FPGA **refuses comparator commands while streaming** (deliberate safety rule) | `setTriggerLevel` during a run means stop, apply, restart (a gap of a few ms). See Q6 |
| LCLKIN | Turned on only during LVDS work (the GPX2 runs warm). The notes measured that LCLKIN off saves little: the GPX2 draws 0.2–0.4 W whenever it is configured | Policy choice. See Q7 |
| Hardware delay / deadtime | Neither exists in the FPGA | Both are done in software, exactly (cheap) |
| Persistence | The FPGA keeps the GPX2 configuration, LVDS phase, comparator settings and run state until it loses power. STATUS reports all of them | Enables "already configured and calibrated" detection with no firmware change (§5) |
| Host code | `host/` holds a tested C++17 library: FT601/D3XX transport, frames/CRC, commands, GPX2 config builder with board rules, record decode, time unwrapping, calibration, `FakeFpga` simulator; 107 checks, ASan/UBSan clean | Reused, not rewritten. See Q11 |

## 4. Architecture

```
FT601 (D3XX, pipelined reads)                       ── reader thread
  → DATA frames (CRC, header checks)                   [tdcctl code, reused]
  → 64-bit records → decode → unwrap → int64 ps        (+ coarse↔GPX2 clock map)
  → per-channel software deadtime, then delay
  → k-way merge with a watermark (time-ordered across channels)
  → tag blocks: {int64 time_ps[], int8 channel[]} + gap/overflow events
                                                    ── processing thread(s)
  → measurement engine: each running measurement consumes the block for its
    own [start, stop) window; synchronized groups share window edges exactly
  → results in C++ buffers
Python (pybind11 module `_dantagger` + pure-Python `Dantagger` package)
  → Swabian names, signatures and keyword names; numpy arrays with
    Swabian's shapes and dtypes; waits release the GIL
```

- **One process owns the board** (D3XX opens it exclusively). A second
  process gets a clear "board in use by PID …" error (lock file).
- **Timeline.** One monotonic picosecond timeline per open board, continuous
  across FPGA runs. The GPX2 keeps measuring between runs, so tags of later
  runs unwrap onto the same timeline through the coarse clock. Results the
  GPX2 held from before a run are dropped by time.
- **Measurement windows in tag time**, as in Swabian. `startFor(d)` covers
  exactly `d` ps of the tag timeline. The run's START/END and TIME markers
  (every 164 µs) advance the timeline even when no tags arrive, so
  `waitUntilFinished` cannot hang on a silent input.
- **Streaming policy (proposal):** the FPGA streams while at least one
  measurement is running, and stops (LCLKIN off) when none are. The scripts
  are a sequence of `startFor`/`wait` calls, so the board is idle between
  points.
- **Backends behind one interface:** `hardware` (FT601);
  `simulated` (synthetic generators: Poisson, pulsed laser + detector with
  jitter, correlated pairs, bursts; a configurable rate, used for tests and
  benchmarks); `fake_fpga` (tdcctl's protocol-level simulator, so the whole
  USB → frame → record → measurement path is tested without hardware);
  `replay` of a recorded `tdcctl stream` run file, in memory only, used for
  tests. No backend writes tags to disk (instruction 8).
- **Performance design:** structure-of-arrays tag blocks of about 64k tags,
  so there is no per-tag virtual call or allocation. Measurements are
  templated hot loops, branch-light, with integer arithmetic only. Bin
  lookup uses a precomputed reciprocal multiply instead of a division.
  Histogram and Correlation keep ring buffers of recent starts and touch
  only the pairs inside the window. HistogramND does single-start
  single-stop per axis with flat row-major bins. Countrate and Counter use
  per-channel counters with a vectorisable channel-to-slot table. Snapshots
  (`getData`) copy under a short lock. Optional worker threads run
  independent measurements in parallel (the N95 has 4 cores).
  Compiled with `-O3 -march=x86-64-v3` (AVX2).
- **Build:** cmake is not installed here. A `setuptools` build calls g++
  directly. pybind11 is vendored as headers (or installed with pip),
  libftd3xx is linked from `TDC_Firmware/third_party`, and the tdcctl
  sources are compiled in.

## 5. Open-time lifecycle: configure and calibrate once per plug-in

`createTimeTagger()`:

1. Open the FT601 (the only one attached, or `serial=`), and refuse it if it
   is not in its recorded configuration (existing tdcctl check).
2. `STOP`, then `STATUS`. This ends any run that a crashed script left
   behind.
3. **Decide "ready"**: the board counts as configured and calibrated when all
   of the following hold:
   - GPX2 flags: configured, verified and measuring, test pattern off;
   - the written GPX2 registers equal Dantagger's default configuration
     (or the `resolution=` variant asked for);
   - the capture format is valid, the LVDS MMCM is locked and IDELAYCTRL
     is ready;
   - the LVDS divider, bit phase, taps and **sampling-phase step** equal
     the values in the host state file
     `~/.local/state/dantagger/<ft601-serial>.json`, which Dantagger writes
     right after each successful calibration.

   A power cycle (unplugging) resets the FPGA: the GPX2 comes up
   unconfigured and the phase step at 0, so the check fails and Dantagger
   runs the full setup. The TDC Control app recalibrating to another phase
   also fails the check, which is harmless: Dantagger simply recalibrates.
4. If not ready: GPX_CONFIGURE (defaults), then LVDS calibration (the
   existing `Session::calibrate`: about 70 phase points × 1 ms plus
   overheads, ~1–2 s in total), then write the state file. Also applied at
   this point: comparator defaults (trigger, hysteresis) and software
   defaults.
5. If ready: skip step 4 entirely (Q9 asks which settings are re-applied
   on every open).
6. `freeTimeTagger()` (or interpreter exit or a crash) stops the run and
   switches LCLKIN off, but **does not reset the GPX2**, so the next script
   skips setup.
7. Escape hatches: `createTimeTagger(recalibrate=True)` and the
   `DANTAGGER_RECALIBRATE=1` environment variable.

## 6. Feature list, sorted from most to least straightforward

**Tier A: trivial (constants, plumbing, bookkeeping)**

1. Import-only names: `Resolution` (Standard/HighResA/B/C),
   `ChannelEdge`, `CHANNEL_UNUSED`, `UNKNOWN`/`LOW`/`HIGH`,
   `LOGGER_WARNING`, `setLogger`. `Combiner`, `Coincidence`, `Scope`,
   `Event` and `TimeDifferences` exist as stubs that raise
   `NotImplementedError` if anyone constructs them.
2. `scanTimeTagger()` (FT601 serials) and `freeTimeTagger()`.
3. `setTriggerLevel` / `setDeadtime` / `setInputDelay` /
   `setDelaySoftware` argument handling, keyword names (`channel=`,
   `voltage=`, `deadtime=`, `delay=`), the matching getters, and
   float-to-integer coercion.
4. Common measurement state: `start`, `stop`, `startFor(d, clear=True)`,
   `clear`, `isRunning`, `waitUntilFinished(timeout=-1)`,
   `getCaptureDuration`.
5. `Countrate`: `getData` (counts / capture duration), `getCountsTotal`.
6. `Counter`: `binwidth`, `n_values`, `getData(rolling=True)` (channels ×
   n_values), `getIndex`, `getDataTotalCounts`.
7. `TimeTagger.reset()`: back to the default settings, without
   recalibrating.

**Tier B: straightforward algorithms that need exact Swabian semantics**

8. `SynchronizedMeasurements`: a proxy tagger that disables autostart and
   registers measurements; `startFor`, `stop`, `clear`, `isRunning`,
   `waitUntilFinished`, all on one window edge.
9. `Histogram`: multiple start, multiple stop, one-sided
   `[0, n_bins·binwidth)`, `getData` int32, `getIndex`.
10. `Correlation`: both signs, `channel_1` stop / `channel_2` start,
    auto-correlation with no self-pairs; the `getIndex` centring convention
    must match Swabian exactly.
11. `HistogramND` (2-D is what is used): single start, first stop per axis,
    row-major flat `getData`, `getIndex(dim)`.
12. `TimeTagStream` + `TimeTagStreamBuffer`: in-memory buffer only,
    `getTimestamps` / `getChannels` / `getOverflows` / `getEventTypes`,
    `size`, `hasOverflows`, `tStart`, `tGetData`.
13. Software input delay (±, up to tens of µs) and software dead time,
    both exact per channel.
14. The simulated backend and its signal generators.

**Tier C: moderate (device and pipeline engineering)**

15. C++ device session on top of the tdcctl host library: open, sync,
    STATUS, pipelined streaming, clean shutdown.
16. Decode → int64 ps unwrap → coarse↔GPX2 clock mapping → timeline
    continuous across runs, with stale-result rejection.
17. Cross-channel merge with a watermark (GPX2 latency bound + the
    largest delay).
18. Streaming policy: run only while measurements run; LCLKIN control;
    stop/apply/restart for comparator changes, with the gap accounted in
    every running measurement (Q6).
19. Overflow handling: OVERFLOW markers become overflow intervals in the
    affected measurements (Swabian-style flags); Countrate and Counter
    stay correct within each interval.
20. The configure-and-calibrate-once lifecycle (§5).
21. pybind11 bindings: numpy outputs with Swabian dtypes and shapes, the
    GIL released in waits, Ctrl+C works during `waitUntilFinished`.
22. Build and packaging without cmake; D3XX linkage; one `pip install -e`
    into `.venv`.
23. Benchmarks and optimisation passes (§7), plus a profile of the full
    tomography measurement set.

**Tier D: needs a decision or the black-box oracle (§9)**

24. Channel numbering and edges (only STOP3 is "falling") (Q1).
25. Trigger requests outside −0.1 … +1.5 V (Q2).
26. Hysteresis default and an API extension for it (Q3).
27. 2.73 MHz start rate above 2.27 M/s per channel → choice of GPX2 frame
    width (Q4).
28. Mapping `Resolution` to the GPX2 HIGH_RESOLUTION setting (Q5).
29. `HistogramLogBins` + `getDataNormalizedG2` + `getBinEdges`. This is
    amcc only, and its normalisation is the one place where the manual is
    thin, so it needs the oracle (Q10, Q12).
30. Exact numeric conventions: bin-edge rounding, non-integer bin widths,
    `getIndex` values, `Counter` bins at window edges. Without the source
    these are taken from the manual and then confirmed black-box (Q12).

## 7. Testing and benchmarking

- **Reference implementations** in plain numpy (brute force, obviously
  correct) for every measurement. Randomised tests compare the C++ results
  with them **bit for bit** on generated streams (Poisson, pulsed,
  bursts, equal timestamps, window edges, channel 1 = channel 2, negative
  delays, overflow intervals).
- **Black-box oracle (if allowed, Q12):** record tag streams with the
  attached Swabian device (`FileWriter`, test signal or real signals), or
  use the existing `fridgeClient/testTags*.ttbin`. Replay them through the
  Swabian library's own virtual tagger, and the same tags through
  Dantagger's replay backend, then compare the outputs of every class and
  method the scripts use. This only runs the library; it never reads its
  source.
- **Protocol-level tests** with tdcctl's `FakeFpga` (frames, markers,
  overflows, run boundaries, comparator changes during acquisition), and
  replay of the real board run `run_20261020_103822.bin`.
- **Benchmarks** (`bench/`, Google-benchmark style, a single N95 core):
  generated streams at 1–50 M tags/s equivalent, realistic window
  occupancy; reports ns/tag and tags/s per stage and end to end.
  Proposed targets, all at least 2× the most the board can ever deliver
  (4 × 2.27 M = 9.1 M events/s, even after a USB 3 upgrade):

  | Stage | Target |
  |---|---|
  | frame check + decode + unwrap | ≥ 50 M records/s |
  | merge (4 channels, delays) | ≥ 30 M tags/s |
  | Countrate / Counter | ≥ 200 M tags/s |
  | Histogram / Correlation / HistogramND (realistic windows) | ≥ 20 M tags/s |
  | end to end, tomography set (Countrate + HistogramND 500² + 2 Counters) | ≥ 10 M tags/s |
  | `getData` of a 500 × 500 HistogramND | < 1 ms |

- **Script acceptance:** the generated usage table doubles as a checklist.
  Every listed script is imported and run against the simulated backend
  with the instruments mocked, which is where `tests/` already monkeypatches
  `TimeTagger`. Then a hardware session with the user: one signal split to
  the Swabian and to the TDC board, with side-by-side runs of
  `takePcr.py`, `correlation.py`, `measureHistogram.py` and
  `tomography_measure_hist.py`.

## 9. Open questions (recommendation first)

**Q1. Channel numbers and edges.** STOP1, 2 and 4 timestamp the rising
edge; STOP3 the falling edge. The 2-D tomography uses channels 2, 4, 3 and
**−1** (a negative pulse's falling edge on input 1).
*Recommendation:* Dantagger channel `n` = physical STOP`n`; channel `-3`
means STOP3; `+3` and any other negative number raise a clear error. A small
`channel_map` in `dantagger.yaml` maps script numbers to physical inputs (for
example `-1 → STOP3`), so the scripts need no edits. You rewire the negative
pulse to input 3.

**Q2. Triggers outside −0.100 … +1.500 V** (−0.15 V in one tomography
config, −0.5 V from `ttHist(invertedTrigger=True)`).
*Recommendation:* raise `ValueError` (never clamp silently), consistent with
the board's safety rule.

**Q3. Hysteresis.** Swabian has none. The board needs a value that neither
blocks 10 mV triggers (75 Ω does) nor chatters on noise (≥ ~2.5 kΩ does).
*Recommendation:* a per-channel default in `dantagger.yaml`, chosen with you
on the bench (only you know the noise floor). Plus a Dantagger-only
extension, `tagger.setHysteresis(channel, millivolts)`, which Swabian
scripts never call.

**Q4. The start channel at 2.73 MHz exceeds 2.27 M events/s per channel**
(44-bit LVDS frames at 100 MHz SDR).
*Recommendation:* make the default GPX2 frame 16 reference-index bits + 18
stop bits = 34 bits. That gives ~2.94 M events/s per channel, a pure
configuration change that the firmware's capture format already supports;
the coarse clock still unwraps easily (8.2 ms index wrap). With 12 + 18 bits
it is 3.3 M/s. Higher rates would need firmware work (DDR LVDS or an event
divider). What is the highest rate you expect on any channel, the start
channel in particular?

**Q5. Resolution.** The scripts never pass `resolution=` (they only print
`HighResB`), so the Swabian default, Standard, is what they get today.
*Recommendation:* the default is GPX2 HIGH_RESOLUTION **off**.
`createTimeTagger(resolution=Resolution.HighResA)` gives 2× and
`HighResB` / `HighResC` give 4×. The datasheet suggests ~9 ps rms at 4×
against ~20 ps off, with the 44 ps comb gone. Do you want 4× as the default
instead? Check: does 4× cost rate or pulse-pair resolution on your inputs?
That should be measured.

**Q6. Changing a trigger while streaming.** The firmware refuses comparator
commands while streaming. In the scripts, triggers change between
measurements, which is fine.
*Recommendation:* if it happens during a run, stop the run, apply the
change and restart. The gap of a few ms is excluded from every running
measurement's capture duration and is flagged like an overflow interval.
Alternative: raise an error. Or change the firmware (yours to decide; it
was a deliberate safety rule).

**Q7. LCLKIN and streaming policy.** *Recommendation:* stream, with LCLKIN
on, only while at least one measurement is running, and stop otherwise (as
in §4). Since LCLKIN saves little heat, the other option is to keep the
board streaming for the whole session, which gives instant starts with no
gaps and costs USB bandwidth and CPU. Which do you prefer?

**Q8. USB speed.** The board enumerated at USB 2 (45 MB/s ≈ 5.6 M
records/s in total). Is a USB 3 port and cable planned? The answer changes
nothing in the design, only how often the FPGA drops under heavy load.

**Q9. Defaults on later opens.** On the first open after plug-in Dantagger
configures the GPX2, calibrates, and applies the defaults. *Recommendation:*
the GPX2 configuration and calibration are skipped on later opens (your
instruction 9). The comparator triggers and hysteresis, and the software
settings (delays, deadtime), are **reset to defaults on every open**, the
way a fresh Swabian tagger starts. They are fast and scripts expect them.
Or should later opens keep whatever the last script left?

**Q10. How "drop-in" works.** Options:
(a) **Recommended:** the scripts stay untouched. A `.pth` hook in `.venv`
makes `import TimeTagger` load Dantagger when `SDE_TAGGER=dantagger` is
set, and the Swabian library otherwise. Both libraries stay installed, and
you pick per run.
(b) Edit the import lines to `import Dantagger as TimeTagger`.
(c) Name the package `TimeTagger` outright, which removes Swabian from this
venv.

**Q11. Reusing the tdcctl host code.** *Recommendation:* build against the
sources in `../FPGA/TDC_Firmware/host` in place, as the single source of
truth, with a check that refuses a firmware design version other than
`0x54440001`. Alternative: vendor a copy with hashes in a PROVENANCE file
(your convention in the FPGA projects). Which one?

**Q12. Black-box conformance against the Swabian library.** Instruction 5
forbids reading its source. Can I *run* it as an oracle (its virtual tagger
replaying `.ttbin` files, recorded with the Swabian device attached here,
serial `22440012ZB`) to confirm exact conventions such as bin edges,
`getIndex`, and the HistogramLogBins G2 normalisation? Without it, those
come from the manual alone, and small convention differences could slip
through.

**Q13. Scope of `drivers/amcc/`** (vendored, a single "Initial Commit"; it
uses `HistogramLogBins`, `TimeTagStream`, `reset`, and channels −2/−4).
*Recommendation:* support what is cheap and also used elsewhere
(`TimeTagStream`, `reset`, `isRunning`, `getCountsTotal`). Implement
`HistogramLogBins` only if you use those scripts.

**Q14. Simulated device in the public API.** *Recommendation:*
`createTimeTagger(simulate=True)` (or `DANTAGGER_SIMULATE=1`) gives a
simulated board with configurable test signals, for running any script
without hardware. Is that useful to you beyond the tests?

## 10. Risks

- **Clock domains.** Event times come from the GPX2 (8 MHz REFCLK) and
  markers from the FPGA's 100 MHz clock. The ppm drift between them is
  tracked continuously. Durations follow the coarse clock, which is fine
  for counting; this needs a test with long silent runs.
- **Stale GPX2 results after LCLKIN was off.** They are dropped by time
  (they unwrap to before the run started). Covered by tests with
