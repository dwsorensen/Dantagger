Inside the host

The PC receives raw records and has to answer one question for each: when, exactly, did this happen? Once every tag has a time on one shared timeline, measurements are just bookkeeping: counts, differences, and bins.

All of it is one C++ core. The app links it directly; Python reaches it through pybind11 with the Swabian Time Tagger API on top. The board's own library (tdcctl, copied from TDC_Firmware) handles USB, frames and commands underneath.

Threads and queues

Three threads, so the USB is never left waiting

Each stage runs on its own thread with a big queue in front of it. A slow stage fills its queue first. Only when every queue downstream is full does the slowdown reach the FPGA, and only then are events lost. Push the input rate, make the PC busy, or add a heavy measurement, and watch where the water rises.

Thread speeds come from the board run of 2026-10-22: at 23.35 M tags/s, dt-receive used 56 % of a core, dt-decode 49 % and dt-engine 61 %. That gives ceilings of about 42, 48 and 38 M tags/s. The engine is the next limit. Before the split, the single-thread design dropped events at 12.6 M/s.
Queue sizes: FPGA FIFO 16 384 records; D3XX 64 transfers in flight plus a 4096-buffer library queue of 4 KiB (≈ 16 MB, TdcOptions::usb_urb_count/usb_queue_buffers); RecordQueue 256 MB of 8-byte records (kRecordQueueBytes); the engine queue's budget 256 MB (kQueueBudgetBytes; Engine::push blocks above it). The decoder pushes a chunk every 32 768 events or 1 ms of coarse time. Thread names show in top -H: dt-receive, dt-decode, dt-engine, dt-recorder, dt-worker.
Decoding

Which lap is it on?

An event's GPX2 time is reference index × 125 000 + stop result, in ps. The index has only 24 bits, so this time starts over every 2.1 s, like a stopwatch that only shows seconds. To know which lap an event is on, the decoder predicts its time from the previous event and the FPGA's coarse clock, then chooses the lap that lands closest. That only works if the prediction is good to well under half a lap.

If the uncertainty is too big, the decoder does not guess. It re-anchors: it places the event at its coarse time, which is good to about a microsecond, and starts a new clock-ratio measurement from there. With the 24-bit default this needs a silence of over an hour. With release 2's 6-bit frame it happened after seconds, which is why 24 + 18 bits became the default.

RecordDecoder::feed (core/record_decoder.cpp): predicted = last_tgpx + dc × coarse_ps × ratio, k = round((predicted − t_cand) / wrap), uncertainty = spread + |dc × coarse_ps| × ratio_unc, re-anchor if uncertainty > 0.45 × wrap. The spread is the worst readout latency difference: (16 + 1) frames × 42 bits × 2 ns + 0.5 µs = 1.93 µs (tdcctl::max_result_latency_us). Compact records add (2¹⁴ + 16) × 8 ns = 131.2 µs, because an event only carries the last marker's coarse time. The ratio (GPX2 ps per coarse ps) is measured from the run's first event every 1024 events once the span exceeds 50 ms, with uncertainty 3 × spread / span + 10⁻⁹. On an anchor, K = coarse × 8000 + coarse_uncertainty − 600 ns − t_gpx, kept at or after the run start, the watermark and the previous event. A fast path takes ratio = 1 while that is provably safe.
Ordering

The watermark and the merge

Each channel's times arrive in order, but the channels arrive late by different amounts, because each has its own readout queue in the TDC chip. The decoder keeps a watermark: a time no future event can come before. Everything earlier than the watermark is final, so it can be merged into one ordered stream and measured. Step through time, or move a channel's input delay.

● received○ still in flight (in the chip's queue, on USB)× removed by dead timefinal: before the watermark + smallest delay
Delays are applied in software and exactly, in the Swabian setInputDelay convention: every tag of the channel moves by the delay. Since every future tag of a channel is at or after watermark + its delay, the merge can only release tags below watermark + the smallest delay. Dead time is non-extending: an event closer than the dead time to the last accepted event of its channel is dropped. Ties are ordered by channel number, as in the Swabian library.
Merger::push (core/merger.cpp). The real watermark is the latest coarse time minus 20 µs (kMarginPs), plus 131 µs for compact runs, minus the clock-ratio error since the last event. A tag a negative delay moves before the run start is dropped. Between runs the timeline is shifted forward if needed so it never goes back. On the run's last chunk everything is flushed.
Windows

A measurement sees only its window, in captured time

The engine hands every merged block to each running measurement, cut to that measurement's window. startFor(d) means d of captured time. If the FPGA run stops in the middle, for example to apply a new trigger level, the window's end moves out by the gap, so the measurement still gets its full duration.

start() and startFor() take effect at the start of the next block the engine processes, or at the start of the next FPGA run if the board is idle. Measurements in one SynchronizedMeasurements group change together under one lock, so they share their window edges exactly. A block is also split around OVERFLOW markers, and each measurement is told about them (on_special). A new run is a discontinuity: pairing state such as a waiting START is forgotten (on_gap).
Engine::dispatch (core/engine.cpp): if (window_seen && block.begin > last_time && stop_time != never) stop_time += block.begin − last_time. This was added after SDE's tomography flow test failed about half the time: a window begun while the previous run was ending lost the gap, so a Counter bin of the window's length never completed.

Changing a setting while measuring

        
The FPGA takes no comparator commands while it streams. So a trigger, hysteresis or LED change means: stop the run, apply the change, start a new run. The measurements keep their data, and their capture time leaves out the gap.

        
The app does this quietly for any setting (SettingsPolicy::restart). Trigger levels, hysteresis, input delays and dead times are shared by all panels and saved for the next session.

        
Python is strict, like the Swabian library. While a measurement you started is running, a setting change raises SettingsBusyError. A measurement that is only running because of Swabian autostart does not block it: the run restarts with a warning.

        
Saving tags. Only the app writes tags to disk, and only when asked. A StreamRecorder taps the raw records on the decode thread, and its own writer thread writes them, so a slow disk never stalls USB. Files are raw FPGA records plus a JSON sidecar. FileBackend replays them through the same decoder. Python never saves tags.
